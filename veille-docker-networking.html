Veille Technologique Docker Réseau

La connectivité
des containers Docker

Comment les containers communiquent entre eux, avec l'hôte et avec l'extérieur. Un tour des trois drivers réseau essentiels — bridge, host et overlay — avec leurs cas d'usage, leurs limites et des exemples de commandes.

Pourquoi le réseau Docker mérite d'être compris

Dès qu'on lance plus d'un container, une question se pose vite : comment est-ce qu'ils se parlent entre eux, et comment est-ce qu'on les rend accessibles depuis l'extérieur ? Docker répond à ça avec un système de drivers réseau interchangeables. Chacun correspond à un besoin différent : isolation sur une seule machine, performance maximale, ou communication entre plusieurs hôtes.

Techniquement, Docker s'appuie sur des briques du noyau Linux : les network namespaces (une pile réseau isolée par container), les paires veth (des câbles virtuels reliant le container au bridge) et des règles iptables/nftables pour le NAT et le filtrage. Pas besoin de maîtriser tout ça pour utiliser Docker au quotidien, mais ça aide à comprendre pourquoi certaines choses se comportent comme elles le font.

1. Le mode Bridge — l'isolation sur un seul hôte

C'est le mode par défaut. Quand Docker s'installe, il crée automatiquement un bridge nommé docker0, et tout container lancé sans précision s'y connecte. Ce bridge agit comme un switch virtuel : chaque container reçoit une adresse IP dans un sous-réseau privé et peut discuter avec les autres containers du même bridge.

Les containers se connectent au bridge via des interfaces veth. Le bridge fait le NAT pour donner l'accès à l'extérieur.

Le bridge par défaut (docker0) a une limite importante : les containers ne peuvent se joindre que par adresse IP, pas par nom. Pour ça, il faut créer un bridge personnalisé, qui ajoute la résolution DNS automatique entre containers.

# Créer un réseau bridge personnalisé docker network create --driver bridge mon-reseau # Lancer deux containers sur ce réseau docker run -d --name db --network mon-reseau postgres:17 docker run -d --name api --network mon-reseau -e DB_HOST=db mon-image # "api" peut maintenant joindre "db" simplement par son nom

Pour rendre un port accessible depuis l'extérieur de l'hôte, il faut explicitement le publier avec -p :

# Le port 80 du container est mappé sur le port 8080 de l'hôte docker run -d -p 8080:80 nginx

2. Le mode Host — la performance avant tout

En mode host, le container partage directement la pile réseau de la machine hôte. Il n'y a plus d'isolation réseau : pas de NAT, pas d'iptables supplémentaire, pas de bridge à traverser.

Aucune traduction d'adresse : le container voit et utilise directement la carte réseau de l'hôte.

# Le container écoute directement sur le port 80 de l'hôte docker run -d --network host nginx # Pas besoin de -p : le port est déjà celui de la machine

L'avantage est la performance : sans overhead de NAT, on gagne généralement entre 5 et 10 % de débit sur une interface à 10 Gbps, et une latence un peu plus faible sur les petites requêtes. Le revers de la médaille, c'est la perte totale d'isolation : un conflit de port avec un autre service de l'hôte peut faire planter le container, et celui-ci a un accès direct aux interfaces de la machine — ce qui est risqué si l'image n'est pas de confiance.

3. Le mode Overlay — relier plusieurs hôtes

Les modes bridge et host fonctionnent sur une seule machine. Dès qu'on a besoin que des containers situés sur des hôtes Docker différents se parlent comme s'ils étaient sur le même réseau local, c'est le rôle du driver overlay — utilisé notamment avec Docker Swarm.

Le réseau overlay encapsule le trafic en VXLAN (port UDP 4789) pour faire transiter les paquets entre les différents hôtes, comme si tous les containers étaient sur le même LAN.

# Initialiser le mode Swarm sur le nœud manager docker swarm init # Créer un réseau overlay docker network create --driver overlay mon-overlay # Déployer un service avec plusieurs réplicas sur ce réseau docker service create --name web --network mon-overlay --replicas 3 nginx

Par défaut, seuls les services Swarm peuvent rejoindre un réseau overlay. L'option --attachable permet aussi à des containers standalone de s'y connecter. Pour les données sensibles, on peut chiffrer le trafic au niveau VXLAN avec --opt encrypted — au prix d'une perte de performance non négligeable, à tester avant de l'utiliser en production.

Comparatif rapide

Driver Portée Isolation Performance DNS entre containers
Bridge Un seul hôte Bonne Légère perte (NAT) Oui (réseau personnalisé)
Host Un seul hôte Aucune Maximale N/A
Overlay Plusieurs hôtes Bonne Correcte (overhead VXLAN) Oui, via Swarm

Quand utiliser quoi

🧩 Bridge
Développement local et applications multi-containers sur une seule machine, par exemple avec Docker Compose.
⚡ Host
Outils de mesure réseau, monitoring système, ou applications à très fort débit qui doivent éviter le coût du NAT.
🌐 Overlay
Déploiements répartis sur plusieurs serveurs avec Docker Swarm, ou services qui doivent communiquer entre datacenters.

Le lien avec mes études

Comprendre comment un bridge Docker fonctionne aide aussi à mieux visualiser comment un switch physique ou un VLAN fonctionne en parallèle.
